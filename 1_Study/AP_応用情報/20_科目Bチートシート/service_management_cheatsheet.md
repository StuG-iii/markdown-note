## **1．読む軸：誰の、何の業務を、いつまでに守るか**

1. 対象：利用者・業務・サービスと、必要な利用時間を確認する。
2. 影響：停止・遅延・誤りで、誰のどの業務が困るかを確認する。
3. 問われた視点：復旧、原因究明、変更、引継ぎ、品質、容量・能力などに分ける。
4. 本文の不備：担当、期限、判断基準、手順、記録、周知のどこが不足しているか探す。
5. 答案：【対象】に【具体的な行動】を行い、【業務上の効果】につなげる。

```text
対象サービス・利用者：
影響を受ける業務・期限：
問われた視点：
本文にある不備・根拠：
誰が・何を・どうする：
得たい効果：
```

「適切に対応する」「関係者と連携する」「品質を高める」だけで止めず、本文の対象・行動を書く。設問が一つだけを問うなら、不要な背景や対策を足さない。

## **2．管理活動の使い分け：目的で判断する**

| 活動               | 主な目的                                                           | 本文の手掛かり                             |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------ |
| インシデント管理   | サービスを早く正常に戻し、業務影響を抑える。                       | 停止、性能低下、暫定復旧、代替手段。       |
| 問題管理           | インシデントの原因・潜在的原因に対処し、発生や再発、影響を減らす。 | 同じ障害の反復、原因分析、恒久対策。       |
| サービス要求管理   | 利用者からの、合意された通常の依頼に対応する。                     | アカウント申請、情報提供、所定の利用申請。 |
| 変更管理／変更実現 | リスク・影響を評価し、承認・調整して変更を行う。                   | 設定変更、パッチ適用、変更要求、切戻し。   |
| リリース管理       | 新規・変更したサービスや機能を利用可能にすることを管理する。       | 提供する変更のまとまり、利用開始、周知。   |
| 展開管理           | 新規・変更した構成要素を対象環境へ導入する。                       | 配布、インストール、適用順序、展開時刻。   |
| 構成管理           | 構成アイテムと、その関係・状態を正確に把握する。                   | CMDB、依存関係、影響範囲、変更後の記録。   |
| サービスレベル管理 | 品質目標を合意・監視・評価し、改善する。                           | SLA、達成状況、報告、レビュー。            |
| 可用性管理         | 必要なときにサービスを利用できるようにする。                       | 稼働率、停止時間、故障・復旧。             |
| キャパシティ管理   | 需要に見合う容量・処理能力を、費用も考えて確保する。               | 応答時間、CPU、メモリ、容量、需要予測。    |
| サービス継続管理   | 大規模障害・災害時も、必要なサービスを継続・復旧する。             | 代替拠点、復旧目標、訓練。                 |

例：サーバ再起動で利用を再開＝インシデントへの復旧対応。メモリリークの原因調査＝問題管理。修正版を評価・承認して適用＝変更に関する活動。一つの障害で複数の活動が関わる。
イベント（状態の変化や通知）がすべてインシデントとは限らない。監視通知の意味と、サービスへの影響を確認する。

## **3．インシデント対応・優先度・エスカレーション**

| 本文の条件                         | 答案につなげる行動                                                     |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 多数の利用者や重要業務に影響する   | 影響度と緊急度に基づき優先度を設定する。到着順だけで扱わない。         |
| 原因究明に時間が掛かる             | 安全性・業務要件を満たす回避策や代替手段で、早期復旧を図る。           |
| 一次窓口では技術的に解決できない   | 専門部署・ベンダへ機能的エスカレーションする。                         |
| 期限超過のおそれ、権限や資源が不足 | 管理者へ階層的エスカレーションし、判断・調整を求める。                 |
| 担当を転送した後、状況が不明       | 対応責任・受付番号・進捗記録を維持し、窓口から利用者へ状況を連絡する。 |
| 技術的復旧だけで終了している       | 業務が正常に再開できたかを確認し、解決内容を記録してクローズする。     |

影響度＝影響する利用者・業務の範囲や重大さ。緊急度＝対応をどれだけ急ぐ必要があるか。
優先度は両者の組合せで決める。数値を必ず掛け算するという意味ではない。
エスカレーションの時期・相手・必要情報・判断権限を定めると、対応漏れや遅延を防ぎやすい。

## **4．サービスデスク・FAQ・引継ぎ**

| キーワード・状況                   | 答案の軸                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- |
| SPOC（単一窓口）                   | 問合せ先を一本化し、利用者が担当部署を判断する負担をなくす。担当者を1人に限定する意味ではない。 |
| 回答が担当者によって違う           | 回答手順・対応ノウハウを共有し、承認・更新の担当と手順を定める。                                |
| 同じ問合せを何度も調査             | 対応履歴を蓄積し、検索可能にして再利用する。                                                    |
| FAQを見ても自己解決できない        | 未解決の問合せの種類・頻度と、検索語・検索結果・回答内容を分析する。                            |
| FAQの用語と利用者の検索語が違う    | 利用者の検索語を基に見出し・説明・同義語などを見直す。                                          |
| FAQの情報が古い                    | サービス変更時の更新、更新責任者、定期レビューを定める。                                        |
| 開発部門から運用窓口へ引き継ぐ     | 初期サポートの実績、未解決事項、手順、連絡先を渡し、窓口が対応できることを確認する。            |
| 専門部署の定型作業を窓口へ移したい | 通常変更のうち、低リスクで手順を定型化し標準変更にできるものを調査する。                        |

FAQの改善は「FAQを充実させる」だけでは弱い。「利用者が解決できなかった問合せの発生頻度を分析し、頻度の高い項目の説明を改善する」のように書く。
本文にないアンケート結果やログ項目を、既に記録されているデータとして扱わない。既存データの分析を問われたら、保存されている項目を使う。

| 指標               | 読み方・注意点                                                                 |
| ------------------ | ------------------------------------------------------------------------------ |
| 一次解決率         | 一次窓口で解決した割合など。専門部署への引継ぎの扱いや分母は問題文に従う。     |
| 初回連絡での解決率 | 最初の連絡で解決した割合。一次窓口での解決と必ずしも同じではない。             |
| 自己解決率         | 利用者が窓口対応を受けずに解決した割合など。対象者・分母・計測方法を確認する。 |
| 応答時間／解決時間 | 受付から初動までと、解決までを区別する。起点・終点は定義を確認する。           |

率だけでなく、再問合せ・利用者満足度なども確認する。早くクローズして件数だけを良くしても、業務が解決していなければ改善とはいえない。

## **5．変更・リリース・展開・構成管理**

| 変更の種類 | 基本的な扱い                                                             |
| ---------- | ------------------------------------------------------------------------ |
| 標準変更   | 低リスクで手順が確立し、事前承認された変更。決められた条件と手順に従う。 |
| 通常変更   | リスク・影響に応じた評価・承認を経て実施する。                           |
| 緊急変更   | 緊急用の評価・承認手順で迅速に実施する。無承認・無記録を意味しない。     |

変更前に確認する項目：

- 対象・目的・実施内容。
- 利用者、関連システム、他の変更への影響。
- リスクとテスト結果、承認者。
- 作業時間・役割分担・利用者への周知。
- 失敗時の切戻し条件・手順・必要時間。
- 実施後の確認方法、記録、構成情報の更新。

「パッチを一斉に適用すると業務が止まる」なら、対象を分けた段階的展開や適用時間の調整を検討する。
「展開管理の視点」が指定されたら、ツールの機能名だけで終えず、「業務時間を避け、対象端末への適用時刻・順序を制御する」のように運用へ落とす。
CMDBは機器の台帳だけではなく、サービス・サーバ・ソフトウェアなどの構成アイテム（CI）と相互関係も管理し、変更の影響分析や障害調査に使う。

## **6．SLA：目標値と測り方を一緒に確認する**

SLA＝サービス提供者と顧客との間で合意した、サービス内容・サービスレベルなどの事項。

| 確認項目     | 例                                                     |
| ------------ | ------------------------------------------------------ |
| 対象         | どのサービス、どの利用者、どの拠点か。                 |
| 提供時間     | 24時間365日か、平日9時〜17時か。                       |
| 指標・目標   | 可用性、応答時間、復旧時間、処理完了時刻など。         |
| 測定方法     | 測定地点、対象期間、起点・終点、平均か最大か。         |
| 除外条件     | 合意した計画停止などを含むか除くか。勝手に除外しない。 |
| 未達時の対応 | 報告、原因分析、改善、責任分担など。                   |

SLAと、部署間の内部合意（OLA）、外部供給者との支援契約の条件に矛盾がないか確認する。外部への応答・復旧約束を内部の作業時間や委託先条件で実現できるかが論点。
障害発生を理由に、直ちにSLAの目標を下げると答えない。まず業務影響を防ぐ対応・代替運用を具体化する。

## **7．可用性・停止可能時間の計算**

\[
可用性[\%]=\frac{合意したサービス時間-停止時間}{合意したサービス時間}\times100
\]

コピー用：`可用性[%] = (合意したサービス時間 − 停止時間) ÷ 合意したサービス時間 × 100`

\[
停止可能時間=合意したサービス時間\times\left(1-\frac{目標可用性[\%]}{100}\right)
\]

コピー用：`停止可能時間 = 合意したサービス時間 × (1 − 目標可用性[%] ÷ 100)`

例：1日8時間、月20日提供、目標可用性99.5%。

1. サービス時間：8×20＝160時間。
2. 停止してよい割合：100%−99.5%＝0.5%＝0.005。
3. 停止可能時間：160×0.005＝0.8時間＝48分。

分母を自動的に24時間×暦日数にしない。サービス提供時間外の停止、計画停止、同時発生した障害の重複時間、端数処理は問題文に従う。
平均値だけで、最大応答時間やピーク時の目標達成を判断しない。

平均故障間隔（MTBF）と平均修復時間（MTTR）を使う基本モデル：

\[
稼働率=\frac{MTBF}{MTBF+MTTR}
\]

コピー用：`稼働率 = MTBF ÷ (MTBF + MTTR)`

MTBFが長いほど故障しにくく、MTTRが短いほど復旧が速い。単位をそろえる。MTTRの名称・測定範囲は資料の定義を確認する。

## **8．要員・工数計算：件数×時間を先に出す**

\[
必要対応時間[時間]=\frac{予測件数\times平均対応時間[分]}{60}
\]

コピー用：`必要対応時間[時間] = 予測件数 × 平均対応時間[分] ÷ 60`

\[
必要人数=\left\lceil\frac{必要対応時間}{1人当たりの対応可能時間}\right\rceil
\]

コピー用：`必要人数 = 必要対応時間 ÷ 1人当たりの対応可能時間（人数は必要に応じて切上げ）`

⌈ ⌉は整数への切上げ。整数人数を求める設問の基本。人月・FTEなどでは小数を扱う場合がある。

例：現在100件／日、20%増加見込み、1件15分、1人が対応できる時間は1日6時間。

1. 将来件数＝100×1.2＝120件。
2. 必要対応時間＝120×15÷60＝30時間。
3. 必要人数＝30÷6＝5人。

「余裕20%」の意味は本文で確認する。

| 指定                                | 上の例での計算           |
| ----------------------------------- | ------------------------ |
| 必要対応時間に20%上乗せ             | 30×1.2÷6＝6人。          |
| 対応可能時間の20%を予備として空ける | 30÷(6×0.8)＝6.25 → 7人。 |

同じ20%でも式は違う。勤務時間と実際に対応できる時間を区別し、休憩・会議・教育・記録作業などが既に控除済みか確認する。
複数種類の要求があるなら「各種類の件数×各平均対応時間」を合計する。
平均工数で人数が足りても、ピーク時の集中、受付時間のカバー、スキル別の担当数などで追加の配置が必要な場合がある。

## **9．キャパシティ・継続・改善**

| 本文の条件                     | 対応の軸                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| CPU使用率や容量が上昇          | 傾向・閾値・到達予測を監視し、枯渇前に対応する。                                             |
| 平均は正常だがピークに遅い     | 時間帯別の需要・同時利用数とボトルネックを確認する。                                         |
| 利用者・処理量が増える         | 将来需要を予測し、必要リソースと費用をキャパシティ計画に反映する。                           |
| バッチ遅延で翌日の業務に影響   | 完了期限と業務影響を確認し、利用部門と処理順序・代替運用などを協議する。                     |
| 一時的にクラウド資源を増強     | 不要になった資源の縮小・解放を検討し、不要な利用料を抑える。縮小可否とデータ保護を確認する。 |
| 監視の誤通知が多い             | 想定された負荷と異常を区別し、閾値・例外条件を見直す。監視そのものを止めない。               |
| 継続計画はあるが訓練していない | 役割、連絡、切替、復旧手順と所要時間を訓練で確認する。                                       |

| 指標 | 問われること                                                                                 |
| ---- | -------------------------------------------------------------------------------------------- |
| RTO  | いつまでにサービスを復旧するか（目標復旧時間）。                                             |
| RPO  | どの時点までのデータを復旧するか（目標復旧時点）。障害前に失ってよいデータの時間幅に関わる。 |
|      |                                                                                              |

継続的改善では、現状を測定 → 目標と改善策を決める → 実施 → 効果を同じ条件で測定 → 見直す。
サービスデスクなら問合せの分類・件数・対応時間・未解決理由など、本文にある記録を根拠に改善対象を選ぶ。

## **10．記述答案と最後の確認**

| 弱い答案               | 具体化した自作例                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------ |
| 関係者と連携する。     | バッチ遅延時の翌日の生産計画と代替運用を製造部・営業部で協議する。                   |
| 引継ぎを徹底する。     | 初期サポートの対応履歴・未解決事項・手順を引き継ぎ、窓口で対応できることを確認する。 |
| FAQを充実させる。      | 未解決の問合せの発生頻度を分析し、頻度の高い項目の説明を改善する。                   |
| 変更を適切に管理する。 | 変更の業務影響と切戻し手順を確認し、所定の承認後に実施する。                         |

例は答案の材料。実際には問われた対象・字数に合わせて必要な部分だけを書く。

- インシデントの早期復旧と、問題の原因究明を取り違えていないか。
- 「展開管理の視点」など、指定された観点に答えているか。
- システムの動作だけでなく、利用者の業務への影響を書けているか。
- 本文にない記録・条件・権限を勝手に追加していないか。
- SLAの対象時間、停止時間の算入範囲、単位を確認したか。
- 工数に将来の需要増加・集中・余裕を反映したか。
- 対策を「誰が・何を・どうする」まで具体化したか。
