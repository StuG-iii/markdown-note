## **1．解く手順：1行 → キー → 関連 → 条件**

1. 結果の1行：顧客ごとか、注文ごとか、商品ごとか、日付ごとかを決める。
2. 元の表の1行：各表が何を1件として保存し、どの列の組で一意になるか確認する。
3. 表を結ぶ：必要な表と結合キーを選び、一致しない行を残すか判断する。
4. 条件を置く：個々の行の条件はWHERE、集計結果の条件はHAVING。外部結合ではONとの違いに注意する。
5. 確認：重複、NULL、0件、複合キーの結合漏れ、並び順を確認する。

```text
結果の1行＝何ごと？：
必要な表・各表の1行：
各表の主キー：
結合する列（複合キーなら全列）：
一致しない行も残す？：
行の条件：
集計単位・集計する値：
集計後の条件：
重複・NULL・0件の扱い：
```

## **2．主キー・外部キー・ER図**

| 用語・本文の条件           | 判断の軸                                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 候補キー                   | 行を一意に決める、余分な列を含まない最小の列の組。候補キーは複数あり得る。                                           |
| 主キー                     | 候補キーから選ぶ。重複不可・NULL不可。                                                                               |
| 複合主キー                 | 複数列を組み合わせて初めて一意になる。                                                                               |
| 外部キー                   | 別の表などの主キー・一意キーを参照して整合性を保つ。外部キー自身は重複し得る。                                       |
| 外部キーとNULL             | NOT NULLなどがなければNULLを許す場合がある。外部キーだから必須とは限らない。複合外部キーのNULLの扱いは定義にも注意。 |
| 1対多                      | 通常、「多」側に「1」側を参照する外部キーを置く。                                                                    |
| 多対多                     | 交差エンティティ（中間表）を置き、二つの1対多に分ける。                                                              |
| 任意／必須                 | 0件を許すか、少なくとも1件必要か。1対多の最大件数とは別に読む。                                                      |
| スーパータイプ／サブタイプ | 共通属性はスーパータイプ、種類ごとの固有属性はサブタイプへ。同じ属性名でも値の意味・定義域を確認する。               |

例：受講者は複数講座を受講し、各講座には複数受講者がいる。同じ組の重複受講はない前提。

| 表     | 主キー           | 外部キー・その他の属性                           |
| ------ | ---------------- | ------------------------------------------------ |
| 受講者 | 受講者ID         | 受講者名                                         |
| 講座   | 講座ID           | 講座名                                           |
| 受講   | 受講者ID＋講座ID | 両IDがそれぞれの表を参照。受講日・成績などを保持 |

同じ人が同じ講座を複数回受けられるなら、上の組では一意にならない。開催番号など、本文の業務ルールに応じた識別項目を検討する。
ER図の主キー下線・外部キー記号・関連線の向きは問題文の凡例に従う。属性名が正しくても指定の下線を忘れない。

## **3．正規化：何が決まれば、何が一つに決まるか**

関数従属性 X → Y：Xが決まるとYが一つに決まる。「番号が分かれば名称が分かる」のように読む。たまたま現在のデータで重複していないことと、業務ルールとして一意なことは別。

| 段階      | 基本問題での着目点                                           |
| --------- | ------------------------------------------------------------ |
| 第1正規形 | 繰返し項目や、1項目に複数の値を詰め込んだ構造をなくす。      |
| 第2正規形 | 候補キーの一部だけに依存する非キー属性を分離する。           |
| 第3正規形 | キーから別の非キー属性を経由して決まる非キー属性を分離する。 |
|           |                                                              |

ここで非キー属性は、どの候補キーにも含まれない属性。第2・第3正規形の説明は、基本問題で使う見分け方。複数の候補キーがある問題は、提示された関数従属性と定義を確認する。

例：明細(注文ID, 商品ID, 注文日, 商品名, 数量)。同じ注文に同じ商品は1行だけ、主キーは(注文ID, 商品ID)とする。

- 注文ID → 注文日：複合キーの一部に依存するので、注文表へ。
- 商品ID → 商品名：複合キーの一部に依存するので、商品表へ。
- (注文ID, 商品ID) → 数量：明細表に残す。

結果：注文(注文ID, 注文日)、商品(商品ID, 商品名)、明細(注文ID, 商品ID, 数量)。
推移的従属の例：社員ID → 部署ID → 部署名。部署名を部署表に分離する。

正規化の目的の答案例：「同じ商品の名称を複数箇所で更新することによる更新漏れ・不整合を防ぐため」。
履歴として保存すべき注文時単価などは、現在のマスタ値と同じ意味とは限らない。項目名だけで削除しない。

## **4．SELECT文：論理的な順序と、条件を置く場所**

基本形の理解順：FROM・JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY。
これは結果を考えるための論理的な順序。DBMS内部の物理的な実行順序を固定するものではない。

| 句・関数   | 役割                                                             |
| ---------- | ---------------------------------------------------------------- |
| FROM／JOIN | どの表の、どの行を組み合わせるか。                               |
| ON         | 結合相手となる行の条件。                                         |
| WHERE      | 集計前の行を絞る。                                               |
| GROUP BY   | 顧客ごと・商品ごとなど、集計単位を決める。                       |
| HAVING     | 合計や件数など、集計後のグループを絞る。                         |
| DISTINCT   | SELECT結果の同一行をまとめる。集計前の水増しを直すものではない。 |
| ORDER BY   | ASCは昇順、DESCは降順。指定しない場合、順序は保証されない。      |
|            |                                                                  |

基本形では、集約関数に入れないSELECT列はGROUP BYに含める。関数従属性を扱うDBMSの拡張等では例外があるため、問題のSQL仕様を優先する。

## **5．結合・集計：0件を残す、重複を増やさない**

| やりたいこと                     | 選択肢・注意点                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------ |
| 両方に一致する行だけ             | INNER JOIN。                                                                   |
| 左表は、右表に一致しなくても残す | LEFT OUTER JOIN。右側の列はNULLになる。                                        |
| 相手の行が存在するかだけ判定     | EXISTS。結合で外側の行数を増やす必要がない。                                   |
| 複合キーで関連する表を結合       | 対応する列をすべてONに書く。                                                   |
| 注文と明細を結合                 | 1注文が明細数分の行に増える。注文金額のSUMは二重計上に注意。                   |
| 二つの「多」側の表を同時に結合   | 組合せで行数が膨らむことがある。必要な単位にそれぞれ事前集計してから結合する。 |
| 日次の表と週次の表を比較         | 比較・結合できる集計粒度にそろえる。                                           |

例の表：顧客(顧客ID, 顧客名)、注文(注文ID, 顧客ID, 状態, 金額)。注文IDは主キーでNULL不可。
要件：「全顧客について、確定注文の件数・合計金額を表示。確定注文がない顧客も0で表示」。

```sql
SELECT C.顧客ID,
       C.顧客名,
       COUNT(O.注文ID) AS 注文件数,
       COALESCE(SUM(O.金額), 0) AS 合計金額
FROM 顧客 C
LEFT OUTER JOIN 注文 O
  ON C.顧客ID = O.顧客ID
 AND O.状態 = '確定'
GROUP BY C.顧客ID, C.顧客名
ORDER BY C.顧客ID;
```

- 全顧客を残すので、顧客を左にしたLEFT OUTER JOIN。
- 状態の条件をONに置き、結合相手となる注文を限定する。
- これをWHERE O.状態 = '確定'に移すと、一致する注文がなくNULL補完された行も除外される。
- COUNT(*)ではNULL補完された1行も数えるので、注文件数0にならない。COUNT(O.注文ID)を使う。
- SUMは対象値がないとNULLになるため、COALESCEで0にする。

集計後に「確定注文の合計が3,000以上」を条件にするなら、GROUP BYの後、ORDER BYの前に以下を置く。

```sql
HAVING SUM(O.金額) >= 3000
```

## **6．NULL・集約・副問合せ：間違えやすいところ**

| 記述                 | 意味・注意点                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| COUNT(*)             | 行数を数える。NULLを含む行も対象。                                                             |
| COUNT(列)            | その列がNULLでない行を数える。                                                                 |
| COUNT(DISTINCT 列)   | NULLを除き、その列の異なる値の数を数える。                                                     |
| SUM／AVG             | NULLを除いて計算。AVGの分母にNULLの行は含めない。                                              |
| IS NULL／IS NOT NULL | NULLかどうかの判定。= NULL、<> NULLでは判定しない。                                            |
| COALESCE(値, 0)      | 値がNULLなら0。0に置き換えてよい業務上の意味かも確認する。                                     |
| NOT INとNULL         | 比較対象にNULLがあると、意図した未該当行が返らない場合がある。不存在判定にはNOT EXISTSを検討。 |

WHEREが残すのは条件がTRUEの行。NULLを含む通常の比較はUNKNOWNになり、TRUEではないので残らない。NULLは0や空文字と同一視しない。空文字の扱いにはDBMS差がある。
集約対象がないと、COUNTは0、SUM・AVGなどはNULLになるのが基本。ただしGROUP BY自体にグループが存在しなければ、そのグループの結果行も出ない。

相関副問合せは「外側の行を固定して、内側を確認する」と読む。実際にDBMSが必ず1行ずつ実行するという意味ではない。

```sql
-- 確定注文が1件以上ある顧客
SELECT C.顧客ID, C.顧客名
FROM 顧客 C
WHERE EXISTS (
    SELECT 1
    FROM 注文 O
    WHERE O.顧客ID = C.顧客ID
      AND O.状態 = '確定'
);
```

- 内側に1行でもあればEXISTSはTRUE。SELECT 1は「1を数える」という意味ではない。
- O.顧客ID = C.顧客IDが「この顧客の注文」を探す条件。この条件を落とすと、別の顧客の注文でも成立する。
- NOT EXISTSにすれば「確定注文が1件もない顧客」。取消注文だけの顧客も含む。
- 「全注文が確定」は「確定注文がある」と同じではない。「未確定の注文が存在しない」ことを調べ、NULLや注文0件をどう扱うかも本文から決める。

その他：

| 用途                 | 基本形・注意点                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| 両端を含む範囲       | BETWEEN 下限 AND 上限。日時列では終了日の時刻にも注意。                                                    |
| 時刻込みで期間を指定 | 開始以上、次の期間の開始未満、という半開区間が使える。                                                     |
| 前方一致／部分一致   | LIKE 'ABC%'／LIKE '%ABC%'。%は0文字以上、_は任意の1文字。                                                  |
| UNION／UNION ALL     | UNIONは重複排除、UNION ALLは重複を残して連結。                                                             |
| 最大値の行を求める   | MAXで値を求めるだけでは、その行の他列は取り出せない。結合・副問合せなどで対応行を特定する。                |
| 再帰問合せ           | 起点のSELECTと、得た結果から次の階層を求めるSELECTを組み合わせる。WITH RECURSIVEなどの構文は問題文に従う。 |

## **7．制約・DDL・スキーマ**

| 用語・構文                 | 意味                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| PRIMARY KEY                | 主キーを定義。重複不可・NULL不可。                                                          |
| UNIQUE                     | 一意性の制約。NULLの扱いはDBMSによる。                                                      |
| NOT NULL                   | NULLを禁止する。                                                                            |
| CHECK                      | 値の条件を定義する。CHECKだけではNULLを禁止できない場合があるので、必須ならNOT NULLも確認。 |
| FOREIGN KEY ... REFERENCES | 外部キーの参照先を定義する。                                                                |
| ON DELETE CASCADE          | 親の参照先行を削除したとき、対応する子の行も削除する。                                      |
| ON DELETE SET NULL         | 対応する子の外部キーをNULLにする。NULLを許す設計が必要。                                    |
| CREATE TABLE               | 表を作る。                                                                                  |
| ALTER TABLE                | 既存の表の定義・制約などを変更する。                                                        |
| スキーマ                   | 表などをまとめる名前空間。スキーマ名.表名で区別する。                                       |

複合外部キーの例：FOREIGN KEY (講座ID, 開催番号) REFERENCES 開催 (講座ID, 開催番号)。対応する列の組と順序を確認する。
会社別スキーマは会社単位の分離・権限制御に使える。ただし分けるだけで全アクセスが禁止されるわけではなく、適切な権限設定が必要。
共有データをどのスキーマに置くか、誰に参照を許すかは本文の要件で判断する。

## **8．トランザクション・排他制御**

| 用語                 | 答案に使う意味                                                                 |
| -------------------- | ------------------------------------------------------------------------------ |
| 原子性（A）          | 一連の処理を全部実行するか、全部取り消す。                                     |
| 一貫性（C）          | トランザクションの前後で整合性の条件を保つ。                                   |
| 独立性／隔離性（I）  | 同時実行するトランザクション間の干渉を制御する。保証の程度は分離レベルによる。 |
| 永続性（D）          | コミットした結果を障害後も保持できるようにする。                               |
| COMMIT               | 更新を確定する。                                                               |
| ROLLBACK             | 未確定の更新を取り消す。                                                       |
| 更新消失             | 同じ旧値を読んだ複数処理が上書きし、一方の更新が失われる。                     |
| デッドロック         | 互いが保持するロックの解放を待ち、進めない。                                   |
| デッドロック予防の例 | 複数資源のロック取得順序を統一する。                                           |
| デッドロック発生後   | 一方を取り消してロックを解放し、必要なら再実行する。                           |
| ロールフォワード     | バックアップ等にログを適用して更新を再現する。                                 |
|                      |                                                                                |

ロック方式の基本モデルでは、共有ロック同士は両立するが、排他ロックは他の共有・排他ロックと両立しない。MVCCでは読み取りの動作が異なるため、問題文の方式を優先する。

在庫10を二つの処理が読み、各々9を書き戻すと、2個売ったのに在庫9になる（更新消失）。本文に応じて、更新前の排他ロック、条件付きの原子的更新、バージョン番号による更新競合検出などを検討する。

| 読取りの問題           | 意味                                                 |
| ---------------------- | ---------------------------------------------------- |
| ダーティリード         | 他トランザクションの未確定データを読む。             |
| ノンリピータブルリード | 同じ行を再読すると、他の更新により値が変わっている。 |
| ファントムリード       | 同じ条件で再検索すると、該当行の集合が変わっている。 |
|                        |                                                      |

## **9．インデックス：検索条件と更新負荷を一緒に見る**

| 本文の条件                   | 判断の軸                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 特定値で少数の行を検索       | B-treeインデックスが有効になりやすい。                                         |
| 範囲検索・並べ替え           | B-treeインデックスの利用を検討する。                                           |
| 絞り込み後も表の大部分を読む | 全表走査の方が速い場合がある。                                                 |
| 複合インデックス(A, B)       | 一般に先頭列Aを使う条件で活用しやすい。Bだけの条件は同様に使えるとは限らない。 |
| 更新・追加・削除が多い       | インデックスの保守コストも増える。不要な追加は性能低下を招く。                 |
| 列を関数で加工して検索       | 通常の列のインデックスを使いにくくなる場合がある。式インデックス等は別。       |
| LIKE '%文字%'                | 通常のB-treeでは先頭からの範囲を絞りにくい。                                   |

インデックスの有無だけでなく、データ量・値の分布・SQL・列順序・実行計画で判断する。「張れば必ず速い」と答えない。
検索条件で残る行の割合が低いことと、値の種類が少ないことは別。用語だけでなく実際の件数を見る。

## **10．最後の見直し**

- 結果の1行は、設問が求めた単位になっているか。
- 複合キーの結合条件が欠けていないか。
- 0件の顧客・売上のない施策など、残すべき行が消えていないか。
- 結合で行が増え、合計・件数が水増しされていないか。
- COUNT(*)とCOUNT(列)、NULLと0を区別したか。
- WHEREとHAVING、外部結合のONとWHEREを区別したか。
- 主キー下線など、ER図の記法指定を守ったか。
