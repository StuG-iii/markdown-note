## **1．最優先：リスク・コントロール・監査手続を書き分ける**

| 問われるもの   | 答える内容                                   | 自作例                                                                                       |
| -------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| リスク         | 何が起き、どんな悪影響があるか。             | 退職者のアカウントが残り、社内情報を不正に閲覧されるおそれ。                                 |
| コントロール   | リスクを予防・発見・是正する仕組み。         | 退職者のアカウントを退職時に無効化する。                                                     |
| 監査資料・証拠 | 判断の根拠になる記録・データ・観察結果など。 | 退職者一覧、アカウント一覧、無効化日時の記録。                                               |
| 監査手続       | 何を、どう調べ、何を確かめるか。             | 退職者一覧とアカウント一覧・無効化記録を照合し、所定の期限までに無効化されているか確認する。 |
| 改善提案       | 不備を是正するため、対象部門に何を求めるか。 | 退職手続とアカウント無効化を連動させ、処理結果を点検するよう提案する。                       |

「アカウントを無効化する」は運用上の対策。「期限までに無効化されたか確認する」が監査手続。監査人が業務の実施責任を引き受ける答案にしない。

## **2．読む手順：あるべき状態 → 不備 → 証拠 → 確認方法**

1. 問い：リスク、コントロール、資料名、監査手続のどれかを確認する。
2. あるべき状態：本文の規程、業務ルール、承認基準、期限、要求事項を拾う。
3. 不備とリスク：誰の何の処理が基準から外れ、何が起こり得るか考える。
4. 証拠：あるべき状態と実際の処理を比較できる資料を探す。
5. 答案：資料名＋方法＋確認事項を、字数に合わせて書く。

```text
問われたもの：
対象業務・担当者：
あるべき状態・基準・期限：
本文の事実・不備：
想定するリスク：
確認する資料：
比較する相手・基準：
確認方法と確認事項：
```

監査手続の基本型：「【資料A】と【資料B】を照合し、【対象・期限・基準】が満たされているか確認する。」
資料が一つで足りる確認もある。機械的に二つの資料を挙げる必要はない。
設問が資料名だけを求める場合は、不要な手順を足さず指定どおりに答える。

## **3．監査人の立場と、整備・運用の違い**

| 項目             | 覚えること                                                                 |
| ---------------- | -------------------------------------------------------------------------- |
| 独立性           | 監査対象から適切な距離を保ち、偏った判断や自己監査を避ける。               |
| 客観性           | 担当者の説明や自分の推測だけで結論を出さず、根拠を基に判断する。           |
| 被監査部門の責任 | 業務を運営し、コントロールを整備・運用し、不備を是正する。                 |
| 監査人の役割     | 証拠を収集・評価し、結果を報告して必要な改善を提案し、改善状況を確認する。 |
| 整備状況         | リスクに対応できるルール・手順・権限・システム機能が用意されているか。     |
| 運用状況         | 決められたコントロールが、対象期間中に実際に実施されているか。             |

承認規程があることと、すべての対象変更で必要な承認を得ていることは別。
規程・手順書の閲覧は整備状況の確認に使える。運用状況は承認記録、変更履歴、点検記録などで確認する。
監査人は助言・改善提案を行えるが、業務の承認や改善策の実施を自ら担って、その仕事を自分で監査する構図を避ける。

## **4．コントロール：何を防ぐ・見つけるか**

| 分類               | 主な働き                       | 例                                         |
| ------------------ | ------------------------------ | ------------------------------------------ |
| 予防的コントロール | 誤り・不正の発生を防ぐ。       | 権限制限、事前承認、入力値の範囲チェック。 |
| 発見的コントロール | 発生した誤り・不正を見つける。 | ログ点検、件数・金額照合、権限棚卸し。     |
| 是正的コントロール | 発見した問題を修正・回復する。 | 誤登録の訂正、権限削除、復旧手順。         |

| 範囲           | 主な対象                                                                           |
| -------------- | ---------------------------------------------------------------------------------- |
| IT全般統制     | 開発・変更管理、システム運用、アクセス管理など、複数の業務処理を支える共通の管理。 |
| IT業務処理統制 | 個々の業務の入力・処理・出力における正確性・完全性・正当性などを確保する管理。     |

分類だけで解答を決めず、本文の仕組みがどのリスクに効くかを確認する。
自動処理でも、設定・マスタ・入力・例外処理が誤っていれば問題は起こる。自動化されていることだけで適切と判断しない。

## **5．本文の不備から引く：リスク・資料・手続**

| 本文の条件                                 | 主なリスク                                 | 資料と確認の例                                                     |
| ------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------ |
| 申請者が自分で承認できる                   | 不正・誤った申請が承認される。             | 権限設定と申請・承認記録を調べ、職務が適切に分離されているか確認。 |
| 退職・異動後も権限が残る                   | 不要な権限で情報にアクセスされる。         | 人事記録とアカウント・権限一覧、変更記録を照合。                   |
| 特権IDを共用する                           | 操作者を特定できず、不正を追跡しにくい。   | 貸出記録・認証記録・操作ログを照合し、実施者と操作を追えるか確認。 |
| 本番変更の承認が不明                       | 未承認・未検証の変更が適用される。         | 変更申請、承認、テスト、本番適用記録の内容・日時を照合。           |
| 手入力や手作業の補正がある                 | 誤入力、処理漏れ、不正な修正。             | 原資料と入力結果・修正履歴・確認記録を照合。                       |
| システム間でデータを連携する               | 欠落、重複、誤変換、反映遅延。             | 送受信記録、件数・金額、取引ID、エラー・再処理記録を照合。         |
| 一部のデータを保留・除外する               | 保留したまま放置され、必要な処理が漏れる。 | 保留一覧と解消・再処理記録を照合し、未処理残を確認。               |
| 規程に合わないパッケージ機能を使う         | 必要な承認・チェックを省いてしまう。       | 差異の評価、適切な時期の例外承認、代替管理策の適用状況を確認。     |
| 定期点検の対象に新システムを追加していない | 未点検のシステムが残る。                   | 最新の対象管理表と点検指示・点検表を照合し、対象漏れを確認。       |
| 改善報告だけで完了扱い                     | 実際には不備が残り、再発する。             | 改善後の設定・記録・点検結果などで是正の実施と有効性を確認。       |

資料名は答案用の一般例。実際の問題では本文・表に示された名称を使う。ログが存在しないのに、既存のログで確認できると決めつけない。

## **6．監査手続の方法：質問だけで終えない**

| 方法                   | 何をするか                                                 | 注意点                                                                    |
| ---------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------- |
| 質問・インタビュー     | 担当者に手順・役割・実施状況を聞く。                       | 説明だけで運用実績を断定せず、必要に応じ記録等で裏付ける。                |
| 閲覧・査閲             | 規程、契約、承認記録、ログなどを調べる。                   | 文書の版、対象期間、承認者、内容も見る。                                  |
| 照合                   | 異なる資料間の対応や一致を調べる。                         | 同じ誤ったデータから作られた二つの資料の一致だけでは不十分な場合がある。  |
| 観察                   | 実際の作業・設備の状態を見る。                             | 観察した時点の状態だけで、過去の全期間の運用を保証しない。                |
| 再計算                 | 計算結果を独立に計算し直す。                               | 入力値・式・端数処理も確認する。                                          |
| 再実施                 | コントロールの手順を監査人が確かめるために再度実施する。   | 対象・環境・権限・業務影響を考慮する。                                    |
| テストデータによる確認 | 正常値・異常値・境界値・条件の組合せを入力して挙動を見る。 | 安全な試験環境等で行う。通ったケースだけで網羅性を判断しない。            |
| ウォークスルー         | 取引の発生から記録・処理・出力までを追跡する。             | 業務の流れと統制点を把握する。1件の追跡だけで全期間の有効性を断定しない。 |

監査証拠は、十分な量と、関連性・信頼性などの質を考えて評価する。単に資料数を増やせばよいわけではない。
抽出して確認する場合は、対象期間、母集団、件数、抽出方法、例外処理を考慮する。特殊な案件だけの結果を、無条件に全体へ一般化しない。

## **7．照合の方向：漏れを探すのか、根拠を探すのか**

| 目的                               | 調べる方向                 | 自作例                                                             |
| ---------------------------------- | -------------------------- | ------------------------------------------------------------------ |
| 完全性：必要な処理の漏れがないか   | 元の資料 → 処理結果        | 支払うべき請求書から支払データを追い、登録漏れを確認。             |
| 実在性・正当性：記録に根拠があるか | 処理結果 → 元の資料        | 支払データから請求書・承認記録をたどり、架空・未承認の支払を確認。 |
| 正確性：値が正しいか               | 対応する項目を比較・再計算 | 請求金額と支払金額、取引先、口座、税額などを確認。                 |

例：元データはA=100円、B=200円。処理結果はA=100円、C=200円。
両方とも2件・合計300円だが、Bの処理が漏れ、Cという別の記録が入っている。件数と合計金額だけで、取引単位の完全性・正当性まで保証できない。
対象ID、対象期間、締め時点、取消・減額・保留などをそろえて比較する。正当な差異と誤りを区別する。

## **8．入力・マスタ・連携・テストの着眼点**

| 対象         | 確認すること                                                         |
| ------------ | -------------------------------------------------------------------- |
| 入力値       | 型、必須項目、値域、桁数、重複、日付の前後、関連項目との整合性。     |
| 入力チェック | 正常値を受け付け、異常値を拒否・警告するか。警告後の処理も確認。     |
| マスタ変更   | 権限、申請理由、承認、適用日、変更履歴、後続システムへの反映。       |
| 処理条件     | 職種・勤務形態・金額など、分岐条件の組合せを漏らしていないか。       |
| 時点         | 変更がいつから有効か、抽出データがいつ時点か、対象期間と一致するか。 |
| エラー       | 検知・記録・担当への通知・原因修正・再処理まで定義されているか。     |
| 再処理       | 処理済みデータの二重登録や二重支払を防げるか。                       |

入力コントロールの例：「標準勤務時間に業務上許されない値を設定したとき、登録を拒否または所定の例外処理に回すか確認する」。
チェック機能の有無だけでなく、具体的な値・条件・組合せと期待される動作を照らして確認する。

## **9．計画・本番移行・委託先・点検の監査**

| 対象               | 確認の軸                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| 開発計画           | 目的・要求事項・役割・費用・日程・リスク・評価方法が定義されているか。                                     |
| 受入テスト         | 業務上の要求と、正常・異常・例外のケースを確認できるか。利用部門の関与も見る。                             |
| 評価基準           | 評価項目だけでなく、合否を判断できる目標値・水準が事前に定義されているか。                                 |
| 本番移行           | 必要な評価を終え、結果に基づいて権限者が移行可否を判断しているか。                                         |
| 導入効果           | 想定した効果を検証できる計画になっているか。移行後に初めて未達と気付くリスクを考える。                     |
| AI・チャットボット | 学習・評価データの対象、季節性、手入力、回答品質、利用範囲を確認する。                                     |
| 委託先             | 責任分担、要求事項、報告・点検・是正の状況を確認する。委託しただけで委託元の管理が不要になるわけではない。 |
| 例外・代替管理策   | 通常の管理策を適用できない理由、承認、代替策、残るリスクと見直しを確認する。                               |
| 点検プロセス       | 最新の対象が含まれ、点検が実施され、不備に対して是正が進んでいるか。                                       |

「回答満足率」は評価項目。「回答満足率が所定の目標以上」は合否判定の基準。名称だけを答えるのか、目標水準を答えるのかを区別する。
改善を支援・指導する管理部門と、改善の実施部門、独立に監査する監査部門の役割を混同しない。本文に指定された担当部署を使う。

## **10．報告・フォローアップ・答案の見直し**

基本的な流れ：予備調査・計画 → 証拠収集・評価 → 結果報告 → 改善状況のフォローアップ。
発見事項は【基準・あるべき状態】【確認された事実】【リスク・影響】【改善が必要な点】を区別して整理する。
被監査部門への事実確認と、監査上の評価を相手の希望に合わせて変えることは別。
改善担当者・期限・進捗・完了証拠を確認し、報告だけでなく不備が実際に是正されたかを評価する。

| 弱い答案                         | 具体化した自作例                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 適切に承認されているか確認する。 | 変更申請と承認・適用記録を照合し、権限者が適用前に対象変更を承認しているか確認する。   |
| データを確認する。               | 元の取引一覧と連携後の登録一覧を取引IDで照合し、欠落・重複がないか確認する。           |
| 点検を実施する。                 | 対象管理表と点検表を照合し、対象の全システムに点検が指示されているか確認する。         |
| 改善されたか聞く。               | 改善報告に加え、変更後の権限設定と運用記録を調べ、不要な権限が残っていないか確認する。 |

実際の答案では字数と問いに合わせて必要部分だけ書く。緊急変更など例外手続が規定されている場合は、その基準に照らして評価する。

- リスクを問われて対策を書いていないか。
- 監査手続を問われて、業務の実施指示を書いていないか。
- 本文の具体的な資料名・対象・担当部署を使ったか。
- 何と何を照合し、何を確認するかが伝わるか。
- 承認の有無だけでなく、対象・権限者・時期も必要に応じて確認したか。
- 規程の存在だけで、運用の有効性を断定していないか。
- 対象期間・基準日・例外・取消・保留を見落としていないか。
- 証拠のない不正や被害を、発生済みの事実として断定していないか。
