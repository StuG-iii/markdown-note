## **1．解くときは「問い → 根拠 → 答案」の3段階**

1. 問い：何の【原因・理由・対策・リスク】か。対象・字数・個数・使用する語句を確認する。
2. 根拠：本文から【攻撃の入口／権限／設定／保存場所／時系列】を拾う。
3. 答案：本文の具体的な対象を入れ、問われた種類の答えで終える。

| 問われ方   | 答案の型                                     | 自作の例                                                   |
| ---------- | -------------------------------------------- | ---------------------------------------------------------- |
| 原因       | 【設定・運用の不備】により【事象】が起きた。 | 退職者のアカウントが有効なままで、不正ログインに使われた。 |
| 理由・目的 | 【防ぎたい事象・得たい効果】のため。         | バックアップも暗号化され、復旧できなくなることを防ぐため。 |
| 対策       | 【対象】に【具体的な操作・設定】を行う。     | 退職者のアカウントを無効化する。                           |
| リスク     | 【誰が・何を使って】【何をされる】おそれ。   | 盗まれた認証情報で、顧客情報を不正に閲覧されるおそれ。     |

「セキュリティを強化する」「適切に管理する」で止めず、何をどうするかを書く。必要な要素だけ選び、字数に合わせる。

## **2．認証・パスワード：何を固定し、何を変えるか**

| 用語・本文の手掛かり                         | 覚えること・答案に使う視点                                                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| ブルートフォース攻撃                         | 一つのIDに対し、多数のパスワードを試す。ID単位のロックアウトが有効な場合がある。                                                 |
| リバースブルートフォース／パスワードスプレー | 一つ・少数のパスワードを多数のIDに試す。各IDの失敗回数が少なく、ID単位のロックアウトを回避し得る。                               |
| パスワードリスト攻撃                         | 他サービスなどから流出したID・パスワードの組を試す。使い回しが被害拡大につながる。                                               |
| 多要素認証                                   | 知識・所持・生体のうち異なる種類を組み合わせる。パスワード＋秘密の質問は両方「知識」。                                           |
| ハッシュ化                                   | 元のパスワードの逆算を困難にする。ただし、候補をハッシュ化して照合する推測攻撃は可能。                                           |
| ソルト                                       | 通常、利用者ごとに異なる値を付加。同じパスワードでも異なるハッシュ値にし、事前計算の使い回しを困難にする。秘密である必要はない。 |
| ペッパー                                     | 秘密の追加値をパスワードDBとは分離して管理。DBだけが流出しても攻撃者が取得できないようにする。                                   |
| ストレッチング／計算コスト増加               | パスワード1候補の検証にかかる計算量を増やし、大量の推測を遅くする。                                                              |

認証＝誰かを確認。認可＝何を許すかを決定。
多段階認証は手順が複数であること。多要素認証と常に同じではない。

## **3．攻撃と対策：攻撃者が何を操作するかで見分ける**

| 攻撃                       | 本文で探す手掛かり                                                 | 対策の軸                                                   |
| -------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| SQLインジェクション        | 入力値をSQL文に文字列連結している                                  | プレースホルダと値のバインドを使う。                       |
| XSS                        | 入力された文字列がページに出力され、ブラウザでスクリプトとして動く | 出力先の文脈に応じてエスケープする。                       |
| CSRF                       | ログイン済み利用者に、意図しない更新リクエストを送らせる           | CSRFトークンを検証する。SameSite属性なども補助策。         |
| OSコマンドインジェクション | 外部入力がシェルのコマンド文字列に入る                             | シェル呼出しを避ける。必要な入力を許可リストで制限する。   |
| ディレクトリトラバーサル   | ファイル名・パスの操作で公開範囲外を参照する                       | 正規化後のパスが許可ディレクトリ内か検証する。             |
| フィッシング               | 偽サイト・偽メールで認証情報を入力させる                           | 正規の接続先を確認する。認証方式の耐性も見る。             |
| ランサムウェア             | データ暗号化、窃取、バックアップの削除・改変                       | 侵入対策、端末隔離、権限制限、保護したバックアップ。       |
| サプライチェーン攻撃       | 委託先・取引先・導入ソフトウェアを経由して侵入                     | 接続権限の制限、委託先管理、更新物の検証、構成部品の把握。 |

対策は固定解ではない。設問が「プログラムの修正」を求めているなら、機器の導入だけで答えない。

## **4．暗号・証明書：どの鍵を誰が使うか**

| 目的                             | 使うもの                                       | 混同注意                                                               |
| -------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| 相手だけに読ませる（公開鍵暗号） | 受信者の公開鍵で暗号化し、受信者の秘密鍵で復号 | 送信者の公開鍵ではない。                                               |
| 署名者・改ざんの有無を確認する   | 署名者の秘密鍵で署名し、署名者の公開鍵で検証   | 署名だけでは内容を秘密にしない。                                       |
| 公開鍵と主体の対応を確認する     | 認証局の署名を検証し、信頼の連鎖を確認         | 証明書の名前・有効期限・失効状況なども確認する。                       |
| 通信経路を保護する               | TLSなど                                        | サーバや端末内のデータまで自動的に保護されるわけではない。             |
| データの変化を検知する           | 信頼できる基準ハッシュ値と比較                 | データと基準値を両方差し替えられる状況では、単純な比較だけでは不十分。 |

短く覚えるなら「秘密に送る＝相手の公開鍵」「署名する＝自分の秘密鍵」。TLSの通信本文には主に共通鍵暗号が使われる。

## **5．機器・仕組み：何を見て何をするか**

| 用語              | 最低限の区別                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| FW                | 主にIPアドレス・ポート番号・通信状態などに基づき通信を許可／遮断する。                                           |
| WAF               | HTTP通信の内容を調べ、Webアプリへの攻撃を検知／遮断する。                                                        |
| IDS／IPS          | IDSは不正通信の検知・通知。IPSは遮断も行う。                                                                     |
| EDR               | 端末の挙動を監視し、侵入後の検知・調査・隔離などを支援する。                                                     |
| SIEM              | 複数機器のログを集約・相関分析し、インシデントの検知につなげる。                                                 |
| URLフィルタリング | 接続先のURLやカテゴリなどでアクセスを制限する。                                                                  |
| ゼロトラスト      | 社内にあることだけで信用せず、利用者・端末・状況を確認してアクセスを許可する。                                   |
| 最小権限          | 業務上必要な対象・操作・期間だけ権限を与える。                                                                   |
| 多層防御          | 複数の対策を組み合わせ、一つが突破されても他で被害を抑える。                                                     |
| SBOM              | ソフトウェアの構成部品・バージョンなどを把握し、脆弱性の影響範囲の特定に役立てる。自動で修正する仕組みではない。 |

基本的な役割の区別。製品によって機能は重なるので、問題文に書かれた機能を優先する。

## **6．インシデント・運用：本文のこの条件を拾う**

| 本文の条件・不備                       | 答案に結び付ける論点                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------- |
| 感染端末がネットワークにつながっている | ネットワークから隔離し、感染拡大や外部送信を抑える。                                     |
| ログの保存容量・保存期間が短い         | 古いログが上書き・削除される前に保全する。                                               |
| 機器ごとに時刻がずれている             | 時刻同期により、機器をまたいだ事象の前後関係を追えるようにする。                         |
| 端末を初期化しようとしている           | 証拠が失われるので、必要な証拠を保全した上で復旧する。                                   |
| バックアップも常時接続・書換え可能     | バックアップまで暗号化・削除されるおそれ。オフライン保管や変更不能な保存方式を検討する。 |
| 最新のバックアップしかない             | 被害発生後のデータで上書きされるおそれ。複数世代を保存する。                             |
| バックアップを取得しただけ             | 復元できるとは限らない。復元試験と所要時間の確認を行う。                                 |
| 管理者IDを共用している                 | 操作者を特定しにくい。個人別IDと操作ログを使う。                                         |
| 異動・退職後も権限が残っている         | 権限の変更・削除を人事手続と連動させ、定期的に棚卸しする。                               |
| 操作ログの監査を利用者に周知する       | 発覚する可能性を意識させ、内部不正を抑止する。                                           |
| 使用ライブラリとバージョンが不明       | 脆弱性公表時に影響範囲を迅速に特定できない。                                             |

デジタルフォレンジックス＝電子的な証拠を保全・分析し、事実関係を調べること。
証拠保全と被害拡大防止を両立する。電源断・再起動は揮発性の証拠を失わせるため、設問の状況や対応手順に従う。
不正のトライアングル＝動機・機会・正当化。

## **7．最後の見直し：この5点だけ**

- 原因を問われて、対策を書いていないか。
- 「サーバ」「データ」だけでなく、本文の対象を特定できているか。
- 理由が「安全性を高めるため」で止まらず、何を防ぐか書けているか。
- 本文にない被害や条件を勝手に付け足していないか。
- 指定字数・解答数・使用語句を守っているか。

情報セキュリティの3要素：機密性＝許可された者だけがアクセスできる、完全性＝情報が正確・完全に保たれる、可用性＝必要なときに利用できる。
