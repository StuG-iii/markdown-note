# 案件着手：考え方と整理のマニュアル

## 目的

案件開始時の目的は、最初から案件全体を完全に理解することではない。

> 分かっていること・分からないことを外に出し、次に実行する30分以内の作業を決める。

「案件を整理する」は大きすぎる作業なので、以下の順序に固定する。

1. 変化を一言で書く
2. 範囲を分ける
3. 利用者の流れを書く
4. 不明点を質問に変える
5. 既存システムへの影響を洗う
6. タスクへ変換する
7. 工数と不確実性を見積もる
8. 次の一手を決める

---

## 1. 考えるときの基本分類

情報は必ず次の4種類に分ける。

| 分類       | 意味                                     | 例                                 |
| ---------- | ---------------------------------------- | ---------------------------------- |
| 事実       | 資料、相手の発言、既存動作などで確認済み | 管理者だけが現在の画面を利用できる |
| 仮説       | 現時点ではそう考えているが未確認         | 既存の権限制御を流用できそう       |
| 未確認     | 誰かへの確認や調査が必要                 | 一般ユーザーにも公開するか         |
| 決定・行動 | 決めたこと、次に実行すること             | 権限仕様を担当者へ確認する         |

### 書き方のルール

- 空欄で放置せず、分からない場合は「未確認」と書く。
- 1行には1つの内容だけを書く。
- 「対応する」「確認する」「修正する」だけで終わらせない。
- 事実と自分の推測を同じ文章に混ぜない。
- 質問と作業を混ぜない。
  - 質問：何を知る必要があるか
  - 作業：その答えを得るために何をするか

#### 悪い書き方

- 権限周りを確認して対応する
- 画面を修正する
- テストする

#### 良い書き方

- 一般ユーザーが画面を閲覧できるか、業務担当者へ確認する
- 検索結果一覧に「ステータス変更」ボタンを追加する
- 権限なしの利用者がURLを直接開いた場合、403になることを確認する

## 2. 案件の変化を一言で書く

最初に、次の3行だけを書く。

```text
現状：誰が、何をすると、どうなるか
変更後：誰が、何をすると、どうなるようにしたいか
目的：なぜその変更が必要なのか
```

### 書き方例

```text
現状：管理者は利用者の詳細画面を開かないとステータスを変更できない。
変更後：管理者が検索結果一覧から直接ステータスを変更できるようにする。
目的：問い合わせ対応時の画面遷移と操作時間を減らす。
```

文章がきれいでなくてもよい。主語と変化が分かれば次へ進む。

---

## 3. 範囲を3つに分ける

案件の範囲は、最初から「対象／対象外」の二択にしない。

```text
対象：今回やること
対象外：今回やらないこと
境界未確定：対象かどうか確認が必要なこと
```

「境界未確定」を設けることで、決まっていないことを無理に確定させずに先へ進める。

### 確認する観点

- 対象の利用者・権限
- 対象の画面・機能
- 対象のデータ
- 対象の処理タイミング
- 対象の端末・ブラウザ
- 対象の運用・リリース
- 既存データの移行有無
- 通知、帳票、外部連携の有無

---

## 4. 利用者の流れで整理する

機能を考えるときは、技術要素より先に利用者の流れを書く。

### 基本の型

```text
誰が
いつ・何をきっかけに
何を入力・選択し
システムが何を処理し
何が表示・保存・通知され
失敗時にどうなるか
```

### 表にする場合

| 観点       | 書く内容                                   |
| ---------- | ------------------------------------------ |
| 利用者     | 誰が使うか                                 |
| 開始条件   | どこから来るか、何をきっかけに始まるか     |
| 入力       | 何を入力・選択するか                       |
| 処理       | システム内部で何を判定・取得・更新するか   |
| 出力       | 画面表示、保存、通知、帳票など             |
| 正常終了   | 成功したことを何で判断するか               |
| 異常・例外 | 入力不備、権限なし、データなし、競合時など |
| 制約       | 性能、期限、ブラウザ、セキュリティなど     |

この段階では、分からない欄に「未確認」と書いてよい。

---

## 5. 不明点を質問へ変換する

思考停止したときは、答えを考え続けず、質問を作る。

### 質問の型

```text
誰が？
いつ？
どの条件で？
何を入力する？
何を表示する？
何を保存・更新する？
何ができる？
何ができない？
成功時にどうなる？
失敗時にどうなる？
権限がない場合は？
同時操作された場合は？
既存データはどう扱う？
誰が運用する？
```

### 良い質問の条件

- 回答によって設計や工数が変わる。
- 誰に聞くか、または何を調べるかが決められる。
- 「念のため」ではなく、確認理由を書ける。
- 一つの質問に複数の論点を詰め込まない。

### 質問の書式

```text
質問：
確認理由：
回答によって変わるもの：
確認先・調査先：
```

#### 質問例

```text
質問：ステータス変更時に変更理由の入力は必須か。
確認理由：画面項目、入力チェック、DB保存項目が変わるため。
回答によって変わるもの：画面設計、テーブル変更、テスト項目、工数。
確認先・調査先：業務担当者、既存の変更履歴テーブル。
```

## 6. 既存システムへの影響を洗う

次の順番で確認する。すべてに変更があるとは限らない。

1. 画面・画面遷移
2. フロント側の入力チェック・表示制御
3. API・サーバー処理
4. DB・SQL・既存データ
5. バッチ・ジョブ
6. 外部システム連携
7. 権限・認証・セキュリティ
8. ログ・監査履歴
9. メール・通知・帳票
10. 性能・同時実行
11. 運用・問い合わせ対応
12. テスト・リリース・ロールバック
13. マニュアル・設計書

### 調査結果の書き方

```text
対象：
現在の仕組み：
今回の影響：
必要な変更：
未確認事項：
```

## 7. タスクへの変換方法

機能を直接細分化しようとせず、必ず次の6工程へ通す。

```text
調べる
決める
設計する
作る
確かめる
反映する
```

### 工程ごとの代表例

#### 調べる

- 類似画面・類似機能を探す
- 関連するクラス、API、SQL、テーブルを特定する
- 権限、ログ、エラー処理の共通方式を確認する
- 開発・テスト・リリース方法を確認する

#### 決める

- 対象範囲
- 画面項目
- 入力チェック
- 処理条件
- 権限
- エラー時の動作
- データ保持期間や履歴
- 対象外

#### 設計する

- 画面・画面遷移
- 処理フロー
- API
- DB・SQL
- 権限
- ログ
- テスト観点
- リリース・ロールバック

#### 作る

- フロントエンド
- バックエンド
- DB変更
- 入力チェック
- 権限制御
- ログ・通知
- テストデータ

#### 確かめる

- 正常系
- 異常系
- 境界値
- 権限
- データなし
- 同時実行
- 既存機能への影響
- レビュー指摘後の再確認

#### 反映する

- リリース手順
- DB反映
- 設定変更
- 本番確認
- ロールバック
- ドキュメント更新

### タスクの書式

```text
動詞 + 対象 + 完了条件
```

#### タスク例

```text
既存の利用者検索画面を調査し、再利用できる画面部品とAPIを一覧化する。
ステータス変更APIを実装し、正常更新と楽観ロック競合を単体テストで確認する。
```

### さらに分解する基準

次のどれかに当てはまる場合は分解する。

- 1日を超えそう
- 完了条件を一文で説明できない
- 調査・判断・実装が一つに混ざっている
- 他者の回答待ちを含む
- 成果物が複数ある
- 不確実性が高い

## 8. 工数見積もりの型

一点だけを当てようとせず、各タスクを3点で考える。

| 値   | 意味                                     |
| ---- | ---------------------------------------- |
| 楽観 | 流用でき、問題なく進む場合               |
| 標準 | 通常の調査・修正・レビューが発生する場合 |
| 悲観 | 想定外、手戻り、追加調査が発生する場合   |

Excelテンプレートでは、次の加重平均を自動計算する。

```text
見積工数 = (楽観 + 4 × 標準 + 悲観) ÷ 6
```

### 工数の前に確認すること

- 何をもって完了とするか
- 類似実績があるか
- 既存部品を流用できるか
- 未確定要件が残っているか
- 外部担当者への依存があるか
- テスト環境・データを準備できるか
- レビューと修正を含めているか
- リリース作業を含めているか

### 見積もれない場合

実装を無理に見積もらず、調査タスクを先に置く。

```text
事前調査：4時間
成果物：影響範囲、実装方針、未確定事項、再見積もり
```

「不明なので見積もれない」ではなく、「何時間調べれば見積もれる状態になるか」を見積もる。

## 9. 思考停止したときの復帰手順

30分進まなければ、次の4行だけを書く。

```text
今分かっていること：
今分からないこと：
それが分かると何が進むか：
次の30分で何をするか：
```

### 次の作業の大きさ

良い例：

- 関連資料を1つ読み、確定事項を3件書く
- 既存画面を1回操作し、入力・処理・出力を書く
- ソースを「status」で検索し、関連クラスを一覧化する
- 業務担当者に送る質問を1件作る

悪い例：

- 案件を整理する
- 仕様を理解する
- ソースを調査する

## 10. 最初の60分の固定手順

|     時間 | やること                              | 完了条件              |
| -------: | ------------------------------------- | --------------------- |
|   0～5分 | MarkdownテンプレートとExcelを複製する | 案件用ファイルがある  |
|  5～15分 | 現状・変更後・目的を書く              | 変化を3行で説明できる |
| 15～25分 | 対象・対象外・境界未確定を書く        | 範囲の仮置きができる  |
| 25～40分 | 利用者の流れと質問を最低5件書く       | 未確認事項が見える    |
| 40～50分 | 影響範囲を各層で確認する              | 調査先の候補がある    |
| 50～60分 | 次の30分タスクを1つ決める             | すぐ着手できる        |

最初の60分の完了条件は、「全容を理解した」ではない。

> 分かっていることと分からないことが分かり、次の30分の作業が決まった。

## 11. MarkdownとExcelの使い分け

### Markdownに書くもの

- 現状、変更後、目的
- 背景や前提
- 利用者の流れ
- 調査で分かった仕組み
- 判断の理由
- 今日の現在地
- 次の一手
- 会話や資料を読んだ直後の粗いメモ

Markdownは、順序立てて考えるための場所として使う。

### Excelに書くもの

- 要件・質問の一覧
- 影響調査の一覧
- タスク一覧
- 工数
- 担当者
- 状態
- 期限
- 依存関係
- リスク・課題
- 件数や合計値

Excelは、項目数が増えた情報を漏れなく管理する場所として使う。

### 二重入力を避ける

- Markdownには詳細一覧をコピーしない。
- Excelには長い背景説明を書きすぎない。
- Markdownから「詳細はExcelの要件ID R-005」のように参照する。
- Excelから「判断理由はMarkdownの『権限方針』参照」のように参照する。

## 12. 必ず使うための運用ルール

1. 案件を受けたら、ソースや資料を開く前にテンプレートを複製する。
2. 空欄を埋め切ることを目標にしない。「未確認」を正しく残す。
3. 調査で分かった情報は、事実・仮説・未確認のいずれかへ書き戻す。
4. 作業終了時は必ず「次の30分でやること」を1つ残す。
5. 30分止まったら、考え続けず復帰手順を書く。
6. 工数には調査、レビュー修正、テスト、リリースを含める。
7. 案件終了後、今回漏れた観点をテンプレートへ1件だけ追加する。

最後のルールにより、テンプレートを案件ごとに少しずつ自分向けへ育てる。
